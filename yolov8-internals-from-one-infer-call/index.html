从一行推理脚本读懂 YOLOv8 内部机制 —— ACL 加载、卷积通道与 84×8400 的来历

Posted on 2026-11-01 In edgePerception
以昇腾板端一行 `outputs = model.run([tensor])` 为线索，逐层拆清 ACL init/load 的资源层级、卷积通道的来源、Backbone/Neck/Head 分工、anchor-free 检测头，以及输出张量 [1,84,8400] 里 84 和 8400 是怎么从 3×640×640 一步步算出来的。

线索代码：昇腾板端推理脚本 infer_yolo_acl.py 里的一行 outputs = model.run([tensor])
目标：不看结论，把 outputs[0] 那个 [1, 84, 8400] 的每一个数字，从最初的 3×640×640 输入推出来

0. 主线概览

一次调用的输入输出极其简单：

但这一行背后串着五个层层递进的问题，本文按这个顺序讲：

  1. 运行时：为什么 load om 之前必须先 init 三连？（ACL 的资源层级）
  2. 模型形态：为什么这块 .om 只吃一张图像 tensor，没有其他参数？（编译期固化）
  3. 数据流水线：卷积把 3 个通道怎么变成几十个通道？Conv2d 的 in/out/k 是什么？
  4. 网络结构：Backbone / Neck / Head 各管什么，边界在哪？
  5. 核心推导：8400 和 84 到底怎么算出来的，每个格点又如何”预测一个框”？

一句话贯穿始终：

.om 是”编译期产物”——形状、输入个数、类别数在 ATC 那一刻全部烧死；ACL 运行时和推理脚本只是”忠实读出并执行”这张图的自描述，对它内容一无所知。

1. 为什么 load 之前必须先 init（ACL 的资源层级）

AclContext 里那三行不是走过场，是在逐级搭建驱动侧的执行环境：

每一层都依赖上一层提供的句柄/资源，是严格父子关系：

步骤 干什么 少了它会怎样
acl.init 加载 ACL 运行时配置、打开与昇腾驱动的通道、枚举设备 acl 模块只是空函数指针，调任何接口都报”未初始化”
set_device(0) 声明”后续操作都对着 0 号 NPU” 多卡时不知道模型下载到哪张卡
create_context(0) 建立执行”会话”：独立内存池、默认 stream、设备访问权限；绑定创建它的线程 模型没有内存池和 stream 可挂载
load_from_file 把图结构+权重 DMA 下载到设备内存、实例化算子、分配 workspace/输出缓存 环境不存在，模型无处可放

为什么 init 必须”手动声明”，不会自动发生

  • ACL 是 C 风格 HAL 库，Python 只是薄绑定：import acl 拿到的是裸 API，没有”import 即初始化”的副作用。用哪个配置文件、用第几号设备、context 建在哪个线程——这些运行时不可能替你猜，所以不提供懒加载。
  • 释放顺序敏感，GC 靠不住：销毁必须严格逆序 unload model → destroy context → reset device → finalize。靠 __del__/GC 自动回收，析构顺序不确定，会崩。所以脚本末尾是手动 model.destroy() 再 ctx.destroy()。

类比 CUDA：cuInit → cuDeviceGet → cuCtxCreate → cuModuleLoad；类比普通文件：先有文件系统和打开的句柄，才能读内容。

2. .om 为什么只吃一张图像 tensor

很多人以为 .om/ACL “规定”了只能输入图像——恰恰相反，“单输入、640×640、一个 float32 图像”是这条导出链决定的，不是格式规定的：

脚本里没有硬编码”必须是图像”，全部是运行时从模型自描述读出来的：

  • model.run([tensor]) 的入参是 list，本来就是多输入通用的：Siamese 双路、音频频谱、点云、LLM embedding，对 ACL 都只是一块指定字节数的 buffer，它不知道也不关心里面是不是像素。
  • 阈值、NMS 这类”旋钮”为什么不在模型里：.om 是纯数值数据流图（固定输入 → 固定输出，中间无运行时可变参数）。conf=0.25、iou=0.45 刻意留在 host 侧后处理里，改阈值不用重编模型。
  • “只允许 640”是默认而非天花板：ATC 默认按静态 shape 编译，喂别的尺寸会在 size 校验处抛 size mismatch（这正是脚本用 letterbox 把任意分辨率补齐到 640 的原因）。但昇腾也支持 --dynamic_input 多档、分档编译，所以”限制”只是这一份编译产物的选择。

3. 卷积与通道：3 怎么变成几十个通道

这是理解后面的地基。

3.1 输入的 3 就是”通道”

“通道”就是”叠了几层”的意思。此时通道数 = 3，因为 RGB 天生三分量。问题是：这个 3 后来怎么变 32/64/128/256？

3.2 唯一规则：输出通道数 = 这一层放了多少个卷积核

一个卷积层做的事一句话：“准备 K 个探针（卷积核），每个探针在整张图上滑一遍、每处打一个分得到一张平面；K 个探针 → K 张平面 → 叠成 K 通道输出。”

关键：核的深度维是用来”吃掉”输入通道的，不产生新通道。在每个位置：

一个核 = 一张平面 [1, H, W]；K 个核 = [K, H, W]。输出通道数只由”这层放了几个核”决定，和输入通道数无关。

3.3 Conv2d(in=32, out=64, k=3) 各参数

参数 含义 决定什么
in_channels=32 输入有 32 通道 每个核必须是 32×k×k（深度对齐，硬约束）
out_channels=64 这层放 64 个核 输出 64 通道，唯一由设计者自由决定的数
kernel_size=3 核空间尺寸 3×3 单视野/感受野大小
stride 每滑几步取一个位置 =2 时尺寸减半（下采样的真正来源）
padding 四周补 0 抵消 -k+1 的尺寸损失，保持同尺寸

参数量：64 × (32×3×3) + 64(bias) = 18496；框架内部把这堆权重存成四维张量 (out=64, in=32, kh=3, kw=3)。

每个核具体长什么样（学成”检测横线”还是”纹理”）是训练时梯度下降自己学的，人没指定；设计者只决定”设几个核”。

3.4 为什么叫 Conv2D：看滑动轴，不看数据维数

Conv*d 里的 d = 卷积窗口”滑动”的空间轴个数：

名称 滑动轴 典型数据 权重张量 rank
Conv1d 1（时间/序列） 音频、文本 3 维 (out,in,k)
Conv2d 2（高、宽） 图像 4 维 (out,in,kh,kw)
Conv3d 3（高、宽、帧/深） 视频、CT 体数据 5 维

图像数据虽是三维张量 [C,H,W]，但只有 H、W 两个轴在滑，C 是被”就地熔化”的深度、不计入巡逻维度 → 所以叫 Conv2d。d ≠ 张量 rank。

3.5 尺寸与通道沿 backbone 的走势

backbone 里穿插 stride=2 卷积做下采样，空间与通道反向变化：

越深的地方要同时跟踪的”概念”越多 → 通道数一路上涨。取某个格子位置竖切一刀得到的那根 C 维向量，就是它”看到的局部世界摘要”，也是第 5 节的起点。

4. Backbone / Neck / Head：网络的三大块

概念上是三大块，”背—颈—头”接起来：

块 职责 输出 是否随任务变 算力占比
Backbone（骨干） “看懂”：把像素加工成语义特征图 抽象特征 P3/P4/P5 不变，最耗算力 绝大部分
Neck（颈） “串”：跨尺度融合浅层细节+深层语义 融合后的多尺度特征 基本不变 小
Head（头） “答题”：把特征翻译成任务答案 检测框/类别 变，且很轻 很小

补充：

  • Stem：backbone 最前端起手的几层卷积下采样（640→320），通常算进 backbone 不单列。
  • SPPF（空间金字塔池化）：backbone 末端一步，用几种核大小各池化再拼接，扩大感受野。
  • Loss head / 辅助头：只存在于训练阶段，导出的 .om 里根本没有，推理时不存在。
  • 网络之外：前处理（letterbox/归一化）在 CPU，后处理（NMS/阈值/坐标逆映射）也在 CPU。

一个诚实的边界问题：Neck 和 Head 在不同框架里会糊在一起。在 ultralytics 源码里 Detect 模块把”Neck（P3/P4/P5 上下采样 concat 融合）”和”Head（每层那个 1×1 卷积）”打包进同一个类，所以 yaml 里只看到 Detect 一个名字，看起来像两大块；但概念上 Neck 确实存在。

落到本项目：Backbone + Neck + Head 全部烧进 yolov8n.om 跑在 NPU 上；脚本里的 preprocess/postprocess 是照着 ultralytics 逻辑用 cv2+numpy 手抄重写的（故意不依赖 torch，避免把几百 MB 推理栈的开销混进被测数据）。

结构 vs 实现的归属：nn.Conv2d 是框架级通用积木（PyTorch 的），ultralytics 的 Conv 是它的封装习惯，yolov8.yaml 里那串缩放系数 + 通道/层数才是 YOLOv8 的设计，而这些数字最终被 ATC 烧进 .om。本项目的推理脚本对结构零改动，全是运行时”读出”。

5. anchor-free 与 P3/P4/P5

5.1 P3/P4/P5 = 特征金字塔（FPN）

命名规则极简：下采样多少倍就叫 P 几。P3=÷8、P4=÷16、P5=÷32。三层一起检测的理由：只在 P5 上，远处小行人不到半个格子细节全丢；只在 P3 上，占满画面的卡车超出单点表达力。于是约定 P3 管小目标、P4 中、P5 大。

5.2 anchor-free 在反对什么

传统 anchor-based（Faster R-CNN / SSD / YOLOv5 及以前）：每格预先绑 9 个手工设定的”锚框”，网络输出的是”把某号锚框挪 dx、放大 sw”的偏移量。代价：锚框尺寸是超参数、换数据集要重新聚类适配；匹配规则全是手工调参；每格预测头数量膨胀 9 倍且大量废框。

anchor-free（YOLOv8/YOLOX/CenterNet）：回到最朴素问法——“你这格中心是不是某物体的中心？如果是，这物体 w、h 是多少？”每格只预测 1 个框（输出 4+类别数，而非 3×9×(4+类别)），真值框中心落进哪格哪格就负责。代价：一个物体只能由中心所在格负责，对长条状/中心模糊的物体表达不如多锚框灵活。

注意：8400×84 这套数字跟 anchor-free 无关——anchor-based 也有多尺度网格，只是每格数字更多、形状不同。

6. 核心推导：84 和 8400 怎么从 3×640×640 算出来

结论公式

6.1 8400 —— 纯空间尺寸的下采样流水

唯一规则：backbone 里每个 stride=2 卷积把 H、W 各砍一半（通道怎么变与此无关，这里只盯尺寸）：

层 stride 尺寸 累计倍率
输入 — 640×640 ×1
L0 Conv 2 320 ÷2
L1 Conv 2 160 ÷4
L3 Conv 2 80 ÷8 ← P3
L5 Conv 2 40 ÷16 ← P4
L7 Conv 2 20 ÷32 ← P5

（中间 C2f/SPPF 的 stride=1，尺寸不动。）所以：

8400 只由 640 决定：换 320 输入就变 40²+20²+10² = 2100。

6.2 84 —— 每个格点要填几个数

固定看某一个格子，它的输出由两组拼成：

  • 4 个框几何量：一个矩形框最少需要 cx, cy, w, h 四个自由度。这是几何常数，与输入尺寸无关。（实现上是”从格子中心向四条边量出的距离 l,t,r,b”，坐标原点由格子位置免费提供，反算加减放在 host 侧后处理。）
  • 80 个类别分：COCO 有 80 类，每类一个独立 sigmoid 分数。80 完全来自数据集类别数——换”人+车”两类，84 立刻变 4+2=6，输出变 [1, 6, 8400]。

6.3 拼成 [1, 84, 8400]

维度 值 来源
batch 1 导出时定 batch=1
特征 84 每格 4 框 + 80 类
格点 8400 P3/P4/P5 格子数之和（源自 640）

三档 8400 格的 84 维向量堆起 → [1, 8400, 84]，导出时转置成 [1, 84, 8400]（这也是后处理开头要 squeeze 去 batch、再 transpose 回 [8400, 84] 才好按列取 [:, :4]/[:, 4:] 的原因）。三个数字来源彼此独立：改输入只动 8400，改类别只动 84，改 batch 只动最前面那个 1。

7. 一个格点如何”预测一个框”

心智模型：格点 = 一根一维特征向量；head 把这根向量翻译成 84 个数。

head 对每根向量做一次线性映射（即 1×1 卷积），实际是两个并行 1×1 卷积：

最关键的一点：这 8400 根向量共用同一对权重——这就是为什么参数量小、为什么叫”卷积”而不是”8400 个独立全连接”。head 学的不是”第 37 号格子的框”，而是”任何一格该怎样从它的摘要生成自己的框“这一条通用法则。

进阶：框分支内部先吐 4×reg_max（默认 16）个分布值，再由 DFL 算子各压成 1 个期望值，对外仍是每格 4 个几何量；DFL 在导出时已烧进 .om，所以输出层只看到 84 而非 4×16+80。

8. 全链路一图流（每个数字都有出处）

  • 8400 ← 只跟 640 有关（尺寸平方相加）
  • 84 = 4 + 80 ← 4 是框的几何自由度（常数），80 是 COCO 类别数（数据集）
  • 1 ← 编译时定的 batch

9. 术语速查

术语 一句话
ACL init 三连 init → set_device → create_context，逐级搭驱动侧执行环境，load 才能把模型放进去
.om ATC 编译产物，形状/输入数/dtype 全部编译期固化，运行时只读不自变
通道 张量”叠了几层”；输出通道数 = 这层放了多少个卷积核
Conv2d 的 in/out/k 输入通道数（硬约束）/ 核个数=输出通道（可自由设计）/ 核空间尺寸
P3/P4/P5 从输入下采样 ÷8/÷16/÷32 的三档特征图，分别管小/中/大目标
anchor-free 每格直接回归 1 个框（无参考锚框），真值中心落进哪格哪格负责
Backbone/Neck/Head 提特征 / 跨尺度融合 / 出答案；YOLOv8 把 Neck+Head 合成 Detect
letterbox 保比例缩放到 640 并补灰边，让静态 shape 的 .om 能吃任意分辨率
DFL 把框分支的距离分布积分成 4 个几何值的内部技巧，已烧进 .om

10. 自测问题

  1. 为什么 acl.mdl.load_from_file 不能在 acl.init 之前调用？load 具体向设备做了哪些事？
  2. 同一块 outputs[0] buffer，按 [1,84,8400] 读和按 [1,8400,84] 读，数值一样但含义不同——这说明了 .om 输出张量的什么性质？
  3. 把一个 YOLOv8n 改成”只检测人、车两类”并以 320×320 输入重新导出，输出张量形状会变成什么？逐项说明每个数字怎么变。
  4. 为什么”一个 3×3×3 核作用在 [3,640,640] 上，输出是 1 张平面而不是 3 张”？
  5. 8400 为什么”只跟 640 有关”，84 为什么”跟输入尺寸无关”？
  6. 既然 ultralytics 能一行推理，为什么本项目脚本坚持用 cv2+numpy 手写前后处理？
