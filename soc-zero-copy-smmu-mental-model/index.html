从 DVPP 零拷贝到 SMMU——SoC 媒体流水线的心智模型

Posted on 2026-10-25 In 芯片与系统
从"DVPP 解码可省 Host 拷贝"这句话出发，一层层拆到 buf/page 分层、IOVA/PA 映射、SMMU 硬件与 context 页表、dma-buf/ION/CMA 分工，直到 codec context 的同名异义与"一颗 IP 能否呈现多实例"——把 SoC 零拷贝媒体流水线背后那套心智模型一次钉死。

0. 一句话主线

在共享 DDR 的 SoC 里，DVPP/ISP/NPU 之间不需要搬字节就能协作，靠的是”预分配固定缓冲池 + 传 dma-buf 句柄 + 每个 IP 在 SMMU 各自的 context 页表里把同一批 PA 映射到不同 IOVA + fence 管复用顺序 + cache 维护保数据新鲜”。所谓”省 Host 拷贝”，省的是跨物理内存边界那一次不得不做的 memcpy，而不是让 AI Core 去共享 codec 的私有堆。

本文按追问顺序展开。每一节都在回答一个具体疑问；所有零件最后拼成第 12 节那张图。

1. DVPP 是什么，”省 Host 拷贝”到底省在哪

DVPP（Digital Vision Pre-Processing） 是昇腾（Ascend）AI 处理器上和 AI Core 并列的一块专用硬件单元，负责：

  • VDEC/VENC：H.264/H.265 硬件编解码；
  • JPEGD/JPEGU：JPEG 编解码；
  • 图像预处理：YUV↔RGB、缩放、裁剪、翻转、叠加等。

在昇腾推理链路里它的位置是：

传统 CPU 软解路径 vs DVPP 路径的对比：

步骤 CPU 软解 DVPP 硬解
解码 CPU 解到 Host 内存 片内 DVPP 解到 Device 内存
预处理 CPU 转色/缩放再复制一份 片内 DVPP 继续处理，就地完成
上传给 AI Core aclrtMemcpy H2D（跨物理内存的大 memcpy） 零拷贝：AI Core 直接按地址读同一块 Device 内存

“省 Host 拷贝”= 省掉了「解码后未压缩的大帧从 Host DDR 搬到 Device 内存」这次大 memcpy，以及 Host 内部多次 buffer 复制。压缩码流本身仍要一次小 H2D 上传，但那远小于原始像素，所以净搬运量大幅下降。

关键前提：昇腾（例如 Atlas 200I DK A2）的 DVPP 单元和 AI Core 挂在同一颗 SoC、共享同一块 DDR——这就是零拷贝能成立的地基。

2. 先把三种地址钉死：VA / PA / IOVA

名字 全称 谁眼里的地址 类比
VA Virtual Address CPU 上进程 桌面上的快捷方式
PA Physical Address DRAM 颗粒真实位置 文件真正躺着的磁盘位置
IOVA I/O Virtual Address 外设 / IP（DMA master） 给”访客”单独画的楼栋图
  • CPU 进程：VA → PA 靠 MMU + 页表。
  • 外设 DMA：IOVA → PA 靠 IOMMU（ARM 上叫 SMMU）+ 页表。

IOVA 本质上就是”设备侧的虚拟地址”。 硬件 IP 只认识 IOVA + 长度，它不知道底下真实 PA 在哪、连不连续。

IOMMU/SMMU 存在的三大价值：

  1. 让 IP 看到连续地址，实际页可以散落各处——上层不用真找一大块物理连续内存；
  2. 安全隔离——每个 IP 或每个 VM 有自己的 IOVA 页表，越界访问触发 fault，不会踩到别人；
  3. 可迁移——物理页搬家（内存整理、CMA 迁移）时只改页表，IOVA 侧完全不变。

常见三种模式：

模式 IOVA vs PA 特点
恒等映射 (1:1 / identity) IOVA == PA 直通，翻译几乎零开销，但没隔离
离散拼连续 连续 IOVA → 多片散落 PA 骗过 IP”以为连续”，最常用
bypass / off 设备直发 PA IOMMU 不介入，性能最高、无保护

3. buf 与 page：两层，不是同义词

这是最容易混淆的分层。 一句话：

buf = 软件语义层的”数据容器”；page = 硬件/OS 层的”内存最小单元”。一个 buf 建立在一组 page 之上，两者由”分配器 + IOMMU 页表”衔接。跨设备共享的是 buf 身份(fd)，复用的是 page，搬运字节只发生在真正跨物理内存时。

页 page 缓冲区 buf
属于哪一层 硬件 / OS 内存管理 软件 / 驱动 / 应用语义
是谁定义的 MMU/SMMU，固定粒度（4KB/16KB/2MB） 程序/驱动，大小随数据（一帧 YUV 可能几 MB）
代表什么 地址翻译与物理分配的最小单位 一段”有含义、有主、有生命周期”的数据
数量关系 一个 buf 通常由很多 page 拼成 一个 page 也可能被拆给多个 buf（少见）

页是砖，buf 是用砖砌出来、有名字有用途的一间房。 房间用哪几块砖是分配器的事，IP 只认房间。

关于”独占”的精确表述

（本节曾有一版表述过头，第 15 节复盘里会详细修正。）正确版：

  • 普通 dma-buf 存活期间，它的 page 是”对 buf 独占”的——buddy 不会再把这些页分给别的分配。
  • 真正的共享发生在 buf 这一层：同一个 buf（同一批独占页）被多个模块同时 import 引用，不是”page 被拆给两家”。
  • 唯一在页级”不铁打独占”的例外是 CMA 和零拷贝网络的 skb page 共享（详见第 5 节和第 15 节）。

4. ION 与 dma-buf heaps：分配器 vs 共享句柄

4.1 ION 是什么

ION 是 Android/Linux 里给硬件外设分配 DMA 内存的分配器框架——把物理内存分配成一个个 buf，导出成 dma-buf fd 让多 IP 共享。它是我们前几轮反复提到的”把 buf 落实成 page、再交给 SMMU 建映射”的那个分配器角色。

普通 malloc 不行，因为 DMA 外设需要：

  • IP 能用 IOVA/PA 直接访问；
  • 可能要物理连续或在特定内存区（无 SMMU 的老 IP）；
  • 能跨进程/跨设备共享同一 buf；
  • 能对齐 cache 属性。

ION 用 heap 抽象不同来源：

Heap 类型 底层来源 用途
ION_HEAP_SYSTEM 内核 buddy（普通页） 通用离散缓冲
ION_HEAP_SYSTEM_CONTIG buddy 连续分配 要求物理连续、无 SMMU 的老 IP
ION_HEAP_CARVEOUT 开机预留区 音视频/ISP 大缓冲，永不迁移
ION_HEAP_TYPE_CMA CMA 区 空闲时可外借、用时迁移回来
ION_HEAP_TYPE_IOMMU 走 SMMU 拼连续 给 IP 一段连续 IOVA

4.2 ION 与 dma-buf 的分工

角色 负责什么
ION / dma-buf heaps 分配器 从物理内存里”变出一个 buf”
dma-buf 共享框架/句柄 把 buf 以 fd 形式跨设备传出去 + 引用计数 + fence 同步

ION 分配的内存通过 dma-buf 导出成 fd。前面说的”传 fd、多方共享、引用计数保命”是 dma-buf 层的机制，”这几页从哪来、连不连续”是 ION 层决定的。

4.3 现状：ION 已被 dma-buf heaps 取代

Linux 5.6+ 起，社区用更轻量的 dma-buf heaps（/dev/dma_heap/xxx）替代 ION。Android 内核已全面转向，但大量老 SoC BSP（含车机、嵌入式）仍在用 ION，概念完全一致，只是 API 换了一层皮。

ION（旧） dma-buf heaps（新）
节点 /dev/ion /dev/dma_heap/system、/dev/dma_heap/cma…
选堆 flags 里指定 heap mask 直接打开对应 heap 的 device 节点
导出共享 走 dma-buf fd 同样走 dma-buf fd
底层来源 一样的 page/CMA/carveout 一样

在昇腾板端上，device 内存里给 DVPP/AI Core 用的那块 buf，是由 ACL 的 device 内存分配器（角色等价于 ION）落实成物理页，再在片上 SMMU 建映射。在 Linux 主线上做摄像头/编解码链路时，真正打交道的是 dma-buf heaps：VIDIOC_REQBUFS 让 V4L2 从 heap 分配一圈 buf，export 成 fd 喂给 NPU——这正是”预分配固定池 + 地址交接”的落地实现。

5. CMA：可迁移的连续内存

CMA（Contiguous Memory Allocator）：开机先”名义上”划出一块区域，平时允许它被普通内存挪用；等有驱动需要物理连续大缓冲时，把里面正在用的页临时搬家（migrate）腾出来交给设备——这块区域里的页就是 CMA 页。

5.1 它解决的两难

老办法 问题
静态 carveout：开机就 memmap 划走 128MB 给设备 设备空闲时纯浪费
运行时 buddy 现找连续页 跑久了碎片化，alloc_contig 常失败

CMA 两头都要：平时能借出去当普通内存用，要用时能收回来且保证连续。

5.2 核心机制

CMA 区的页被标记为 MIGRATE_TYPE_MOVABLE。当驱动申请一块 CMA 连续缓冲时，内核：

  1. 挑出一段连续页范围；
  2. 对范围里正被占用的 movable 页逐个 migrate（复制到新页、改页表、释放原页）；
  3. 腾出的整段连续物理页交给驱动，pin 住供 DMA 用；
  4. 设备用完 → 解除 pin → 页回到 movable 池，又可外借。

5.3 关键含义：为什么”CMA 页”和”迁移窗口”重要

  • 普通 dma-heap/buddy 分配的 buf：页一旦被 buf 拿去就钉死独占。
  • CMA 分配的 buf：它的页坐落在”和普通内存共用”的迁移区里。只有在被分配并 pin 住（长周期 pin_user_pages）之后才受保护；pin 之前内核理论上还能迁移这块区里的页。

这就是”buf 声称持有页”和”这块区还能被回收/搬动”之间的时间窗口——靠 pin 关掉。媒体 DMA 在传前一定先 pin，pin 上了迁移就被挡，此时才等价于”独占”。

5.4 与 IOMMU 的对照

CMA 和 IOMMU 是解决”设备想要连续内存”的两条路线：

  • 有 SMMU → 用离散页拼连续 IOVA → 不必真连续，不太需要 CMA；
  • 没 SMMU 的老 IP → 靠 CMA 给真物理连续页。

现代 SoC 有了 SMMU 后，CMA 主要留给没有 IOMMU、或要求真物理连续的场景。

6. SMMU 是硬件 IP：TCU + TBU + micro-TLB

SMMU 是 SoC 里一颗实实在在的硅块（一块 MMIO 地址映射的硬件单元），坐在每个设备到 DRAM 的 DMA 事务通路上。 软件（Linux 的 arm-smmu / arm-smmu-v3 驱动）只配置它，翻译真由它执行。

6.1 硬件组成

硬件部件 干的活 纯软件能做吗
TCU 拿 SID → walk Stream Table→STE→CD→页表，查不到就 fault ❌ 每笔事务实时处理
TBU 每个母设备前放一个，micro-TLB 缓存最近翻译 ❌ 每 cycle 判定
Table Walker 主动从 DRAM 读页表（多级），自己发内存读请求 ❌ 硬件状态机
Command Queue (SMMUv3) 从内存拉软件下发的 cmd（TLB invalidate 等） ❌ 硬件消费队列
Event Queue / Pri Queue 硬件把 fault/缺页写回内存供软件处理 ❌ 硬件产生

关键直觉：一次 DMA 从设备发出到落到 PA 是在流水线关键路径上、每笔事务都要完成的——软件永远追不上，只有硬件能承担。CPU MMU 是硬件，SMMU 同理，只是主语从进程换成了设备。

6.2 软件负责什么

软件不干翻译，只做三件事：

  1. 在 DRAM 里”造表”：Stream Table、CD、context 页表都是普通内存数据结构，由软件按 Arm 架构规定的格式填，硬件 table walker 自己去读。页表格式和 CPU stage-1 完全一致——因为两者是同一份规范。
  2. 配置寄存器：告诉硬件 Stream Table 基址在哪、SID→STE 映射、bypass 默认与否。
  3. 消费 fault event queue / 下发命令：硬件报的越界、缺页由驱动处理；TLB 失效等通过 Command Queue 让硬件执行。

分工总结：硬件执行翻译/缓存/报错，软件构造数据表/下发指令/善后故障。

6.3 一个容易被忽略的实际后果

SMMU 自己也要发 DMA 去读 DRAM 里的页表（table walk 的内存流量）。这带来：

  • miss 时延迟高：TBU miss → TCU 去 DRAM 做多级 walk，可能十几个 cycle 到几微秒——“让池子小、TLB 常驻热”就是为此；
  • 页表本身要落在 SMMU 可达且不被 cache 藏起来的区域：驱动填完页表要 dsb/flush 再让硬件读到新值。

6.4 各家实现

Arm 官方 IP：MMU-600（SMMUv3）、MMU-500/600。自研兼容 SMMU：Qualcomm 的 SMMU、NVIDIA Tegra SMMU、三星 Exynos sysmmu 等。服务器 Arm（Neoverse）走标准 SMMUv3。

7. SMMU 为什么叫 SMMU 不叫 IOMMU，以及”实例”的层次

7.1 命名：概念 vs 实现

类别（generic） 各家实现（brand）
CPU 侧 MMU ARM MMU-600、Intel 某实现
设备侧 IOMMU Intel VT-d / AMD AMD-Vi / ARM SMMU

IOMMU 是通用概念，SMMU 是 ARM 在这个类别下的产品/规范命名。 Linux 内核也印证：设备树写 arm,smmu，驱动代码在 drivers/iommu/arm-smmu-v3.c——功能归类是 iommu 子系统，ARM 的实现叫 SMMU。

7.2 为什么用 “System” 而不是 “I/O”

“I/O” 来自 x86/PCI 世界：CPU 有 MMU，另外再给 I/O 总线上的外设（主要 PCIe） 配一个 MMU。设备在芯片外、挂在总线上。

“System” 来自 ARM SoC 世界：需要翻译的不是外部 I/O 卡，而是 SoC 内部一大片共同访问”系统内存 (system memory = 主 DRAM)”的总线 master：

这些 IP 不是挂在外部 I/O 总线上的”外设”，而是系统内的对等 master。用 “System MMU” 描述”给全系统各 master 管理到系统内存的地址”更贴切。

7.3 “SMMU 实例”到底指什么——四个层次

“实例”不是简单=物理 IP 数量。分四层看：

层级 “多实例”从哪来 物理 SMMU IP 数
裸金属 host = 硬件颗数 多
虚拟化 guest（vSMMU/virtio-iommu） 陷入+模拟 / 嵌套 Stage-1(S1)+Stage-2(S2) 1 颗可以看起来是 N 颗
PASID/SVA 同一 SID 下多 CD（一设备多地址空间） 1 颗里 N 套地址空间
TCU/TBU 分布建模 寄存器/驱动节点拆分 1 颗 IP 报成多驱动节点

大 SoC 常放多颗物理 SMMU IP，按功能分区（如多媒体一颗、外部 PCIe/NIC 一颗），原因：互连位置避免通路瓶颈、SID 空间与流表规模、故障域解耦、带宽/时延就近化。Linux 侧现象：/sys/kernel/iommu_groups/* 分成多组，dmesg 里多个 arm-smmu probe（不同 MMIO 基址）。

虚拟化层特别值得记：硬件 SMMUv3 支持 Stage-1+Stage-2 两级——Stage-1 由 guest 自己管（guest VA→IPA），Stage-2 由 hyp 管（IPA→PA）。一颗物理 SMMU 就能同时服务多 VM 各自独立 context，这是”一个 IP 承载多实例语义”的硬件根据。ARM 生态里这套叫 vSMMUv3，Linux/KVM 已支持；还有半虚拟化旁路方案 virtio-iommu。

8. Stream Table 与 context 页表

8.1 Stream Table：每个 SMMU 实例一张的公共索引

Stream Table 是”电话簿”，不是”内容本身”——它只做”SID → 属于哪个 context”的路由；真正的 CD 和 context 页表另外存在。

关键要点：

  • 公用：同一个 SMMU 实例只有这一张流表。
  • 索引键是 SID：PCIe 设备的 SID = BDF(bus/device/function)；片内平台设备的 SID 由固件（DT/ACPI）分配一个 RID。
  • 登记发生在 attach 时：驱动给某设备建 context 后，把”SID → 这个 context”写进 STE。
  • 不是整颗芯片一张：多颗 SMMU 硬件就有多张流表。

8.2 STE 的三种条目

STE 配置 含义 有没有独立 context 页表
Translate 正常走 CD→context 页表翻译 ✅ 有
Bypass 直通，设备直接发 PA，不翻译 ❌ 无
Abort 禁止该设备访问，fault ❌ 直接挡掉

不是每个 IP 都注册了 context——有些老 IP 或信任 IP 配的是 bypass，根本没有自己的页表 context。

8.3 多设备共享 context 就在流表层面体现

几个设备的 STE 指向同一个 CD，它们就共享同一套 IOVA 空间、同一本 context 页表——这就是”整条媒体流水线共用一本页表省映射”的落地实现。反过来要隔离就把它们各指向不同 CD。

流表本身常做成两级以应对稀疏 SID 空间：L1 Desc(SID高位) → 直指向 STE 或 → L2 表(SID低位) → STE → CD → 页表。

8.4 context 页表：翻译的真正本体

context = 某个设备/域的私有地址空间；context 页表 = 实现这个地址空间的多级翻译表。一次翻译要穿三层数据结构：

Context Descriptor 里存了什么：

字段 含义
TTBR0 / TTBR1 页表基址（和 CPU MMU 一样分两个半区）
TCR 翻译控制：页表级数、粒度（4KB/16KB/64KB）、IOVA 位宽
MAIR 内存属性（缓存/共享性）
Stage 配置 用 stage-1 / stage-1+2
ASID 地址空间 ID，给 TLB 打标记避免串味

页表本体和 CPU 页表几乎同构——ARM SMMU 故意复用 CPU (ARMv8-A) 的页表格式：

支持 block descriptor 大页（2MB/1GB）减少表项。学过 CPU 页表的人，几乎可以平移到”context 页表”，只是主语从进程换成了设备。

“每个 context 一本”的隔离本质：

两个设备的 IOVA 完全不同，但页表项都指向同一批 PA_0/PA_1。 一本页表 = 一个设备能看到的”世界”；设备只能访问自己这本页表里映射过的 IOVA，查不到就 fault。网卡再坏也只能在它自己的 context 页表里打转。

9.2 车机 SoC 里的多方 fan-out

一颗 SoC 上 sensor 采集进来的一帧 就是一个 buf（一组固定物理页），同一时刻被四个 IP 各自 import、各自建 IOVA→PA、同时 DMA 读它：

  • 谁都没有拷贝这帧数据，只是各自 import 了同一个 fd；
  • SMMU 在各自的 context 页表里给同一批物理页建了 IOVA→PA；
  • 四个 IP 各发一份 DMA 请求，走各自的 TBU（micro-TLB 命中就直通，miss 就 walk 一次），最终读到同一份数据。

9.3 关于”时间锁/并行”的常见误解

有人担心”共享 buf 会给产物上时间锁、不能并行”——错。要拆三件事：

A. 读同一份数据 = 完全并行，不存在时间锁。
四个只读消费者读同一份不可变数据，天然可并行。fence 在这里的作用不是”让它们排队”，而是”保命”：只要还有一个读者没读完，这个 buf 就不能被回收/覆盖。它是生命周期守卫，不是互斥锁。

B. fence 真正会”卡一下”的唯一时机：复用同一个 buf 时。


这是写与复用的顺序约束，靠多缓冲池消解：池开够大（4~8 块），codec 去写 buf[i+1]、别等 buf[i]，稳态下 fence 等待被流水线吃掉。

C. “每个产物需要单独一份 buf，有写消耗”——对，但不是零拷贝的代价。

数据角色 是否各自要独立 buf 为什么 和零拷贝有关吗
输入帧（被多方读） ❌ 共享一份 只读，大家看同一份 零拷贝省的就是把输入复制进各家缓冲
输出产物（各家写的结果） ✅ 各自要一份 ISP/NPU/VENC 结果本就是不同东西 无关，本来就要写自己的结果

零拷贝省的是”把输入复制进各家缓冲”的输入拷贝（原本 4 次几 MB memcpy 变 0），并不给输出加税。

D. 真实并行上限来自 DRAM 带宽，不是锁。
四路并发读会分摊内存带宽，各自有效吞吐下降——靠 QoS 仲裁、优先级、错峰管理，而不是拷贝或加锁。

9.4 为什么”每帧 SMMU 频繁重映射”是伪命题

进入稳态后，映射按 buf 建一次、池循环复用：

  • 每帧切换的只是”指针”，不是”映射”；
  • 整条媒体流水线的 IP 常共享同一个 SMMU 域/页表（第 8.3 节），或对 DMA 区用 1:1 恒等映射——交接 buf 时连”跨 context 再映射”都省了；
  • TLB 友好：池就那几个 buf（典型 4~16 个）反复循环，地址工作集小且固定，页表项/TLB 一直是热的。

代价转移到了哪里：从”搬字节”转移到”fence 同步 + cache 维护“。

问题 为什么 解法
脏读/旧数据 codec 写进的是 device 侧物理页，AI Core 若走 CPU cache 或 IP 自带 cache，可能读到上一次循环的残留 交接时做 cache clean/invalidate（或该 DMA 区直接 non-cached 映射）
覆盖竞争 codec 想复用 buf[i] 时，得确认 AI 已经读完 buf[i] fence / sync-point（dma-buf fence、EGLSync、各家媒体 SDK 的 release fence）

9.5 什么时候”还是得拷”——诚实边界

  • 独立 PCIe 加速卡（Atlas 300 训练卡、独显 GPU）：卡上有独立显存，Host DDR 和 Device 显存是两块物理内存，跨 PCIe 的 H2D 拷贝无法避免——这才是”必须搬”的真实来源；
  • 数据格式/内存排布不匹配：DVPP 输出 tile/块状（YUV420SP、UV0V）若模型要 RGB 连续排布，可能需要一次 device 内重排（仍在片内，不是 Host 拷贝，但会有 device 内读写）；
  • 跨 VM / 跨安全域：虚拟化或 ASIL 分区之间，为隔离强制显式搬运或共享受控 buffer。

9.6 流水线哲学一句话

预分配、循环复用、地址交接、fence 保序——所有跨 IP 的”接力”都围绕一个固定 buffer 池转，映射和分配是 setup 时一次性的，帧级的活儿只剩”填地址寄存器 + 等/发一个 fence”。

10. Codec 的 “context” 同名异义

视频编解码里也有”context”这个词，但它和 SMMU context 不是一回事。

SMMU context Codec context
是什么 某设备的私有地址空间 某次编解码的算法/会话状态集合
核心内容 CD + 它指向的 IOVA→PA 页表 编码参数、熵编码状态、DPB、工作缓冲、RC
谁在用 硬件 SMMU 做地址翻译 编解码 IP + 它的驱动/SDK 做计算
目的 隔离 + 翻译 DMA 地址 持有有状态计算的中间态

Codec context 里到底装了什么

视频编解码（H.264/H.265/AV1）是强状态机：

  • 配置：分辨率、profile/level、QP、熵编码模式（CABAC/CAVLC）、GOP 结构；
  • 熵编码器状态：CABAC 概率模型跨宏块/跨 CTU 累积更新，初始化 = 重置这套模型；
  • 参考帧管理（DPB）：帧间预测要用前面若干帧；
  • 码率控制（RC）：上一帧用了多少 bit、缓冲满度，决定下一帧 QP；
  • 片上 scratch/工作缓冲：IP 内部做 DCT、运动估计用的暂存区。

单帧 vs 流水线：差的正是”要不要每次重建 context”

单帧/one-shot（JPEG 图片编解码、逐帧图像任务）帧间无状态延续，每次新开一个 context——重置熵编码模型、申请工作缓冲、配置参数。开销摊在”初始化”上，吞吐低。

流水线/流式（视频码流）context 只初始化一次、跨帧保留状态，每帧只是往里喂 in-buf、取 out-buf。这正是第 9.4 节讲的固定缓冲池 + 地址交接能发挥的场景——context 热着，帧级活儿只剩填寄存器 + fence，setup 成本被整段码流摊薄。

一点点交集（不改变”两个不同 context”的结论）

初始化 codec context 时，如果它要申请新的工作缓冲，会顺带触发 dma-heap 分配 + 在该设备的 SMMU context 里建映射。也就是说：

  • codec context 的 reset/init 是主成本（算法状态重建）；
  • 它可能连带做几页内存的分配和地址映射（碰到 SMMU context 的页表增项）。

这是”一件事引发另一件事”，但不能因此说两者是一个意思——一个是算法状态包，一个是地址空间，只是在同一次 setup 流程里前后脚发生。流水线模式下这两件事都被一次性做完然后长期复用。

“context” 是被用滥的多义词

以后还会在各种层看到它，含义都是”干这件事所需的状态包”：

场景 context 装什么
进程 context task_struct + 页表(mm) + 寄存器组
线程 context 寄存器栈 + TLS
CPU MMU context 页表基址 + ASID
SMMU/设备 context 地址空间 + 页表（第 8 节那本）
GPU/EGL context 命令流状态 + 该进程的地址空间绑定
Codec context 编解码算法状态（本节）
网络会话 context 连接五元组 + TCP 状态 + 拥塞窗口

共同骨架：“先把背景状态准备好，才好让每次操作只做增量、而不必每次从零开始。” 看到 “context” 就条件反射问一句：谁的 context？装的是哪一层的？

13. 七问自测（脱稿版）

按你既有的”七问脱稿验收学习自测规则”，下面这七问能不看文档口述出来说明这一套模型已经内化：

  1. “DVPP 省 Host 拷贝”具体省的是哪一次拷贝？为什么压缩码流还是要拷？
    → 答：省的是”解码后未压缩大帧从 Host DDR 到 Device 内存”这次大 memcpy；码流本身小，仍要一次 H2D 上传，但净搬运量大幅下降。

  2. buf 和 page 分别在哪一层？一个 buf 是不是独占它的 page？
    → 答：page 在硬件/OS 层，buf 在软件/驱动/应用语义层。普通 dma-buf 存活期间它的 page 是对 buf 独占的；真正的共享在 buf 层——多模块 import 同一个 buf、共享引用计数与 fence。

  3. IOVA 和 PA 之间靠什么翻译？SMMU 的 TCU 和 TBU 各干什么？
    → 答：靠 SMMU/IOMMU + context 页表。TCU 是中央控制器，负责 walk 页表；TBU 分布式部署在每个设备前，含 micro-TLB 缓存翻译结果。两者都是硬件。

  4. Stream Table 是不是整颗芯片只有一张？context 页表和 CD 什么关系？
    → 答：每张 SMMU 实例一张（多颗 IP = 多张流表）。CD 存 TTBR 等配置，指向 context 页表；页表本体是 IOVA→PA 的多级翻译结构，格式和 CPU stage-1 页表同构。

  5. 多 IP 共享同一批物理页时，SMMU 里发生了什么？帧级会不会频繁重映射？
    → 答：各 IP 的 context 页表里各插入若干”IOVA→同一批 PA”的表项；帧级不重映射，只切”选哪块 buf”的寄存器指针。池小 → TLB 常驻热。

  6. 零拷贝下”多方共享 buf”会不会造成时间锁、不能并行？
    → 答：读 fan-out 完全并行，fence 只是生命周期守卫不是互斥锁；只有”写者复用同一 buf”才短暂等 fence，靠多缓冲池消解。真正的并行上限来自 DRAM 带宽竞争，不是锁。

  7. codec context 和 SMMU context 是同一个东西吗？”SMMU 实例数”是不是恒等于物理 IP 数？
    → 答：不是——codec context 是算法状态包（CABAC/DPB/RC/工作缓冲），SMMU context 是地址空间+页表。实例数分层看：裸金属通常 = 物理 IP 数，但虚拟化下 1 颗 IP 可呈现 N 颗 vSMMU；PASID 让 1 颗里长出多套地址空间；分布式 TCU/TBU 建模也让软件层”实例”数不同。

15. 复盘：两处「初判有误」的修正

按项目复盘规范，独立记录本轮讨论中我说过头/说满的两处、根因、修正过程与教训。它们不是小瑕疵，而是”默认场景 = 全部真相”这个思维惯性的两个具体表现——正是这类讨论里最容易掉进去的坑。

15.1 修正一：「一个 buf 活着不代表它的 page 独占」——按字面过头

  • 现象：讨论 buf/page 分层时，我说”一个 buf 活着，不代表它的 page 独占”，想强调”引用计数管生命周期”。用户一句”有这么夸张吗”把我拦下。
  • 根因（三环节）：
    1. 混淆了两个不同层次的”共享”：page 级（页被拆给两家）和 buf 级（同一个 buf 被多方 import 引用）。我把 CMA、skb 那类页级共享的例外当成了 buf 的常态表述。
    2. 类比”引用计数”时滑向”引用计数的对象不独占”的直觉，忘了独占性作用在页→buf 这一边，多路引用作用在 buf→多消费者那一边。
    3. 想一句话讲清”buf 和 page 是两层”时用力过猛，宁可”制造惊讶”也不肯平铺直叙。
  • 修复：把话精确化为——“普通 dma-buf 存活期间它的 page 是独占的；真正发生的共享在 buf 层，是同一个 buf（同一批独占页）被多个模块同时 import 引用”；然后单独保留两个窄例外（CMA 迁移窗口、skb 页共享）作为脚注，避免再滑回”常态”。

  • 前后对比：

    | | 原表述 | 修正后 |
    |—-|—-|—-|
    | 页独占性 | “一个 buf 活着不代表它的 page 独占”（过头） | “普通 dma-buf 的 page 是独占的；只有 CMA/skb 这类窄场景存在页级迁移/共享” |
    | 共享发生层 | 含糊 | 明确：buf 层被多方 import 引用，不是 page 层被拆 |
    | 保护机制 | “引用计数保证被读完前不归还”（对，但归因错） | 页受分配器独占保护；跨消费者时序靠 dma-buf 引用计数 + fence |

  • 教训：讨论”分层”时特别容易为强调分层而故意夸张。修正动作是每提出一个反直觉断言，立刻在脑中问：”这句话的字面范围有多大？例外在哪？”——把它们显式列出而不是让断言滑过去。

15.2 修正二：「多个 SMMU 实例=多颗硬件，不存在一个 IP 虚拟出多实例」——只在裸金属层成立

  • 现象：讲完 SMMU 是硬件 IP 后，我用”实例=一颗物理 IP”作为默认。用户反问：”并不存在一个 IP 虚拟出多个 SMMU 实例的场景？”——我又说满了。
  • 根因（三环节）：
    1. 把 Linux host 侧看到的”iommu_device 数”直接等价成”物理 IP 数”——忽略了虚拟化/半虚拟化层。
    2. 忽略了 SMMUv3 硬件本身天生支持 Stage-1+Stage-2 嵌套、PASID 让 1 SID 下多 CD——硬件早就允许”一颗承载多实例语义”，软件视角完全依赖你怎么建模。
    3. 忽略了 Qualcomm 那种 TCU + 分布式 TBU 各自有 MMIO 的实现，Linux 侧看到多驱动节点但物理上是一张大 SMMU 的情况。

  • 修复：明确分出四层”实例”来源并各自标注物理 IP 数：

    | 层级 | “多实例”从哪来 | 物理 IP 数 |
    |———|————————|—————-|
    | 裸金属 host | 硬件颗数 | 多 |
    | 虚拟化（vSMMU/virtio-iommu + Stage-1/Stage-2） | 陷入+模拟 / 嵌套翻译 | 1 → N |
    | PASID/SVA | 同 SID 下多 CD | 1 颗里 N 套地址空间 |
    | TCU/TBU 分布建模 | 寄存器/驱动节点拆分 | 1 颗 IP 报成多驱动节点 |

  • 前后对比：

    | | 原表述 | 修正后 |
    |—-|—-|—-|
    | 实例语义 | 实例=物理 IP，一一对应 | 实例数取决于看它的层；4 种来源各自成立 |
    | 一颗 IP 是否只能一个实例 | 是（过头） | 否。虚拟化 + PASID + 分布式建模都能让一颗 IP 呈现”多实例” |
    | 硬件能力 | 未提 | 明确 SMMUv3 天生支持 S1/S2 嵌套、PASID 多 CD |

  • 教训：讲硬件抽象时，“默认场景”要显式限定作用域。裸金属 host 只是四层里的一层；讨论”实例”这种软件-硬件耦合概念时，起手就该问：”谁眼里的实例？ guest？host？驱动？固件？”

15.3 两次修正的共同模式

两处过头都不是知识错，而是表达时把”我默认讨论的那一层”当成了”所有层”。这是学习/讲解硬件抽象概念时最容易犯的错误：抽象层数一多，人倾向把最外层的具体数字当成常量。

可复用规则：

每当给出一个”X 就是 Y”的强等价断言时，在同一句话里附上”在哪一层这样等价”（”在裸金属 host 视角下…”、”对普通 dma-buf 而言…”）。这样即便边界条件被忘记，作用域也自带刹车，滑不成”永远如此”。

16. 收尾

回到最初那句话：“DVPP 解码可省 Host 拷贝”——它背后站着的完整模型是：

  • 两种地址：VA / IOVA / PA；IOVA→PA 由硬件 SMMU 翻译；
  • 两层内存：page（硬件/OS） vs buf（软件语义），buf 独占 page，共享发生在 buf 层；
  • 两个协作框架：ION/dma-heap（分配器）+ dma-buf（共享句柄+引用计数+fence）；
  • 两条竞争路线：SMMU 用离散页拼连续 IOVA vs CMA 用迁移拿真物理连续页；
  • 一次 setup 一次性映射：固定缓冲池循环复用 + 传 fd + 每 IP 在自己 context 页表建 IOVA→同一批 PA；
  • 帧级只剩三件事：填寄存器指针、发/等 fence、cache clean/invalidate；
  • 一个反直觉澄清：多方读同一帧是并行的，fence 是生命周期守卫不是互斥锁；并行上限来自 DRAM 带宽不是”时间锁”；
  • 一个同名异义提醒：codec 的 context 是算法状态包，SMMU 的 context 是地址空间；
  • 一个”实例”分层看：裸金属=物理颗数只是最外一层；虚拟化、PASID、TCU/TBU 建模都能让一颗 IP 长出多实例语义。

这套心智模型不是昇腾专属——任何共享 DDR 的多 IP SoC（车机、手机、边缘 AI 芯片）都用同一套 dma-buf + SMMU + 固定池 + fence 的骨架。看清这一层，DVPP 与 ISP/NPU/VENC 的每一次协作就不再是”魔法”，而是可以被拆开、被量化、被调试的具体机制。
